What does a training framework actually manage for us?

PyTorch combines multidimensional data, differentiable operations, registered model state, parameter updates, execution modes, and portable checkpoints. The framework automates mechanics—not the engineering decisions around them.

01

PyTorch turns the mechanics from Lessons 2–7 into managed runtime state

A training framework does not replace models, shapes, loss, chain rule, or optimization. It represents those concepts and coordinates their state so engineers can build larger systems without hand-writing every derivative and matrix operation.

Tensor system

Stores values with shape, numeric type, device, and memory layout.

Autograd engine

Records differentiable operations and applies reverse-mode differentiation.

Module system

Registers nested parameters, persistent buffers, and mode-aware behavior.

Optimizer system

Transforms gradients into parameter updates and may retain update history.

Serialization system

Saves and restores portable model and training state.

Metaphor: an instrumented factory

Tensors are labeled material containers, modules are registered machines, autograd records how material moved, the optimizer adjusts machine settings, and checkpoints capture restorable factory state.

Where the metaphor stops: tensors can share storage and participate in symbolic derivative graphs; optimizers use numerical state rather than physical maintenance; and saving a checkpoint does not preserve arbitrary external data or code automatically.
Code-readiness boundary: this lesson teaches PyTorch's concepts and execution order without requiring Python. Engineering Lab A, after Lesson 10, teaches the minimum syntax, environment, error-reading, and test workflow before students modify a training program.

02

A tensor carries values plus execution metadata

Shape tells us how values are organized. Dtype tells us how each value is encoded. Device tells us where computation and storage occur. Gradient tracking tells autograd whether operations should be recorded for backward use.

Metaphor: a labeled shipping container

The contents are numerical values. Shape is the packing arrangement, dtype is the item format and size, device is the warehouse, and gradient status says whether custody history must be recorded.

Where the metaphor stops: tensor operations can create graph relationships, views can share underlying memory, and device transfers perform real data movement.

Why dtype matters

Floating-point tensors

Represent continuous values and support ordinary gradient-based learning. Lower precision saves memory and can accelerate supported hardware, but narrows numerical range or precision.

Integer tensors

Represent counts, indices, token IDs, and class labels. They do not ordinarily carry continuous gradients because infinitesimal integer changes are not defined.

Value memory is only the beginning. Training also stores parameters, gradients, optimizer state, saved forward activations, temporary workspaces, and allocator overhead.

04

A module is a registered tree of model state and behavior

PyTorch modules organize layers into a hierarchy. Registration lets the framework discover parameters, move them between devices, change mode recursively, collect state, and give an optimizer the intended trainable tensors.

Metaphor: an asset registry, not merely a folder

Putting a machine in a registered factory inventory makes it discoverable for maintenance, relocation, configuration, and backup. An unregistered object may exist but be missed by those operations.

Where the metaphor stops: module registration follows specific object relationships, and arbitrary application state does not become model state automatically.

Parameters and buffers are not the same

Parameter

Persistent tensor intended to be optimized, such as a weight or bias. It normally requires gradients.

Persistent buffer

Saved model state not updated by the optimizer, such as certain running statistics or masks.

05

The training loop is an ordered state machine

Every stage assumes the previous stage produced specific state. Changing the order is not stylistic: it can use stale gradients, step before gradients exist, or measure the wrong loss.

06

Training and evaluation modes change selected layer behavior

Switching a module to evaluation mode does not disable autograd. It changes mode-aware layers such as dropout and batch normalization. Disabling gradients controls graph recording. These controls are separate.

Dropout primer

During training, dropout randomly hides some activations and rescales the survivors so units cannot rely on exactly the same partners. During evaluation, the full learned network is used for stable output.

Batch-normalization primer

During training, batch normalization uses the current batch and updates stored running statistics. During evaluation, it uses those stored statistics so one prediction does not depend on its temporary batch companions.

Forward reference: Lesson 10 teaches dropout, normalization, and regularization in depth. Here you only need their state contract: their behavior changes with training versus evaluation mode.

MODE BEHAVIOR LAB

Send the same input through dropout repeatedly

The conceptual layer has four activations [2, 2, 2, 2] and drops half during training while rescaling survivors.

Training mode

Dropout samples masks; batch normalization updates and uses batch statistics. Repeated outputs may differ.

Evaluation mode

Dropout is disabled; batch normalization uses stored running statistics. Repeated outputs should be stable for stable inputs and parameters.

Quiet failure: validation in training mode may be noisy or update running statistics. Inference with gradient recording may still produce correct values but waste memory. Test both mode and gradient context explicitly.

07

A checkpoint is a versioned state package—not the whole application

For portable restoration, save structured state and enough metadata to reconstruct its meaning. The required contents depend on whether the goal is inference or exact training continuation.

CHECKPOINT PLANNER

Choose the restoration goal

Model state

Registered parameters and persistent buffers, keyed by module path.

Optimizer state

Update history associated with parameters, needed for faithful continuation.

External metadata

Architecture/configuration, preprocessing, label map, versions, metrics, and data identity.

Common checkpoint failures

Architecture mismatch

Saved keys or shapes do not match the reconstructed module.

Missing preprocessing

Weights receive features encoded differently from training.

Partial resume

Weights load, but optimizer, scheduler, epoch, or random state does not.

Unsafe provenance

An untrusted serialized artifact can be a supply-chain risk. Load only trusted formats and sources.

State dictionaries are necessary, not sufficient. They do not automatically capture the model class, feature contract, package versions, dataset, training code, or business evaluation evidence.

Prerequisites: Complete the core interactions first.

Autograd records differentiable operations and accumulates gradients into leaf parameters. Modules register parameters and buffers; optimizers own update state; train/eval modes alter dropout and normalization. These boundaries remain separate even when one framework presents a unified API.

Devices, dtypes, mixed precision, compiled graphs, and distributed state affect correctness and speed. Forgetting to clear gradients changes the effective batch; using training mode during evaluation changes behavior; weights without preprocessing or labels preserve shape but lose meaning.
